# 분산 트랜잭션 구현 · 최적화

## 요약

구현

- 재고(로컬) → 계좌(gRPC) → 배송(Kafka) 순서로 서비스 호출
- UX 흐름상 계좌 서비스까지는 동기적으로 처리 + 피벗 트랜잭션
- 배치 재시도, 일부 수동 처리가 필요한 케이스는 모니터링 알림

구현 결과

- RPS 40으로 개방형 부하 테스트
- 과부하 상태에서도 트랜잭션 자체는 안정적으로 처리
- avg 1064ms, p99 2056ms

최적화 결과

- 메시지 배치 처리, 폴링 주기 최적화 진행
- avg 1064ms → 164ms (85% 감소)
- p99 2056ms → 305ms (85% 감소)
- RPS 40 → 60 (50% 증가)

## 요구사항

주문 서비스 구현

1. 주문 요청
2. 재고 서비스에서 재고 차감
3. 계좌 서비스에서 금액 차감
4. 배송 서비스에서 배송 진행

구현 목표

- 유지보수성 관리를 위해 MSA 채택
- 서비스 안정성 : 정합성, 가용성
- 대용량 트래픽 : 확장성, 고성능
- 트랜잭션 목적에 맞춰 **안정성**을 최우선으로, 대용량 트래픽 처리는 차순위로 한다
- 전체 작업 흐름에서 에러 발생, 서버 다운 시나리오를 가정한다

## 오케스트레이션

### Saga 패턴 유형

- 코레오그래피 방식은 흐름을 추적하기 어렵다
- 오케스트레이션 방식은 흐름을 한 곳에서 추적하므로 유지보수가 용이하며
- 특정 애플리케이션에 여러 오케스트레이션 로직이 집중되는 형태가 아니라면, 심각한 단일 장애 지점이라고 보기 어렵다고 생각된다
- 따라서 **오케스트레이션** 방식을 채택한다

### 트랜잭션 구성

| 비즈니스 로직 | 분류 | 근거 |
|---|---|---|
| 재고 서비스에서 재고 차감 | compensable | 재고가 언제 추가될 지 알 수 없음 |
| 계좌 서비스에서 금액 차감 | pivot | 잔고가 언제 충전될 지 알 수 없음 |
| 배송 출발 | retriable | 재고가 존재한다면 재시도 가능 |

### 오케스트레이션(주문) 위치

- 새로운 주문 서비스 도입은 비용이 크므로 선택지에서 제외한다
- 보상 트랜잭션을 최소화 할 수 있는 위치에서 오케스트레이션한다
- 확장성을 확보하기 위한 의존성 흐름을 고려한다
- 계좌 서비스에서 사용자 식별이 이루어진다면, 재고 서비스는 기존에 계좌 서비스를 의존할 가능성이 높다
- 따라서 오케스트레이션을 **재고 서비스**에서 구현하며, 출금 로직을 피벗으로 관리한다

### 마이크로서비스의 성공/실패

| DB 업데이트 | 응답 | Saga 상태 업데이트 | 후속 처리 |
|---|---|---|---|
| ○ | ○ | ○ | 다음 단계로 진행 |
| ○ | ○ | × (saga 다운) | 실패처리, 보상/재시도 |
| ○ | × (트랜잭션 이후 실패) | - | 실패처리, 보상/재시도 |
| × | × | - | 실패처리, 보상/재시도 |

- 로컬 트랜잭션이 성공하고 응답 처리에 성공한 경우 성공으로 간주된다
- 로컬 트랜잭션이 커밋되었으나 응답에 실패할 수 있다 (aftercommit 등)
- 재시도 처리를 할 수 있을지 장담할 수 없다
  - 내부 로직으로 인해 발생한 버그인 경우 지속적으로 실패할 가능성이 있기 때문이다
  - 일부 수동 처리가 필요한 케이스의 경우 모니터링을 위해 지속적인 실패 로그를 남길 필요가 있다
- 보상 처리시 DB 업데이트를 원상복구해야 한다
  - 보상 처리도 **재시도** 가능해야 하므로, 멱등으로 구현해야 한다
- saga가 다운되면 응답 결과가 유실되어 성공 여부를 알 수 없으므로 실패처리한다
  - 출금 결과가 기록되지 않은 채 35초가 지난 주문은 **스케줄러**가 보상한다
  - 35초 = 동기적 호출 타임아웃 + 커넥션 대기 시간 + 여유 시간
- 보상 처리는 피벗까지의 단계에 적용하며, 피벗 이후 단계는 항상 재시도한다
  - 재고가 존재하면 배송은 실패할 수 없기 때문이다
  - 만약 판매자의 실수 등으로 인한 조치가 필요한 경우 수동으로 처리한다

### 오케스트레이션 흐름

오케스트레이션 도중 실패시 오케스트레이션 상태에 따라 보상/재시도 처리한다

- 피벗까지 상태인 경우 보상 진행
- 피벗이후 상태인 경우 재시도

1. 주문 엔티티 생성과 재고 차감을 하나의 로컬 트랜잭션으로 처리하고 SAGA 상태를 업데이트한다
2. 계좌 서비스를 동기적으로 호출하고 SAGA 상태를 업데이트한다 (피벗)
3. outbox를 생성하고 SAGA 상태를 업데이트해 배송 서비스를 비동기적으로 호출한다

## 통신 · 인프라

### 이벤트 구조 vs gRPC

- 계좌 서비스는 UX상 동기적인 흐름을 요구하므로 gRPC로 구현한다
- 배송 서비스는 비동기적으로 이루어지므로 메시지 브로커를 통해 구현한다

### 메시지 브로커

- 오픈소스인 Kafka, RabbitMQ 중 하나를 선택
- MSA 도입이 필요한 대규모 서비스이고, 재처리 구현 및 확장성 측면에서 Kafka 채택한다

### 릴레이 모델

- Polling 방식은 스케일 아웃이 용이하나 병렬 실행시 이벤트 순차 발행을 보장하지 않는다
- Log Tailing 방식은 스케일 아웃이 어려우나 이벤트를 순차적으로 발행한다
- 같은 엔티티를 수정하는 트랜잭션 T1, T2는 **커밋 순서**에 따라 이벤트가 발행되어야 한다
- 이벤트 순서를 보장하는 Tailing 방식을 채택한다

### 기타 구현 방식

- 각 서비스는 서로 분리된 DB에 대한 권한을 가진 멀티 모듈로 구현
- 계약 관리는 별도 계약 모듈과 계약 테스트 중 유지보수 편의성을 고려해 계약 모듈로 채택
- 피벗 단계까지 동기적으로 처리하는 gRPC 도입을 위해 Temporal, Eventuate 없이 직접 구현
- 단일 인스턴스(로컬)에서 간단하게 실험하는 목적이므로 Docker Compose 채택
- Tailing 릴레이는 Debezium 오픈소스로 구현

## 정합성

### 격리성 문제

- 각 로컬 트랜잭션이 순차적으로 처리되는 중 중간 상태 누출로 인한 Dirty Read가 발생할 수 있다
- Non-Repeatable Read, Phantom Read, Lost update 문제도 발생한다
- 로컬 트랜잭션 내부에서 조회와 수정이 동시에 이루어지도록 설계해야 한다

Countermeasure

- semantic lock : 해당 레코드를 잠근다
- reread value : 레코드를 다시 읽고 값이 변경된 경우 SAGA를 중단한다
- pessimistic view : 데이터 갱신을 가능한 재시도 가능한 트랜잭션으로 변경한다
- commutative updates : 어떤 순서로 실행해도 같은 결과가 나오도록 설계한다

### 멱등성

- `order_id` 를 포함한 멱등키로 구현한다
- 로컬 트랜잭션 내에서 처리가 어려운 서로 다른 서비스 간 로직에서 구현한다
- 요청 멱등은 구현하지 않고, 서로 다른 주문이 두 번 요청된 것으로 간주한다

### 실패 처리

- 비즈니스 로직 실패시 사용자에게 실패 원인을 설명한다
- 기타 에러로 인한 실패시 잠시 후 다시 시도해달라고 응답한다
- Kafka에서 기타 에러 발생시 기본 재시도 옵션을 사용한다

### 실험 환경

- 로컬 부하 테스트 (JVM Runner)
- CPU 2.3GHz 6코어 12스레드
- 메모리 WSL 8GB 할당
- Docker Compose 기반 컨테이너 환경

### 예상되는 한계

- 동일한 머신에서 부하를 생성하므로 네트워크 지연 시간이 포함되지 않는다
- 로컬 환경이므로 각 컨테이너가 같은 리소스를 공유한다
- 따라서 실제 프로덕션 환경과는 성능 차이가 존재할 수 있다
- 로컬 트랜잭션 지연에는 커넥션 풀 대기 시간이 포함되지 않는다

### 측정 지표

| 지표 | 정의 | 지연 시간 |
|---|---|---|
| RPS | 초당 종료된 요청 수 | 요청 시각 → 응답 시각 |
| TPS 주문 | 초당 종결된 주문 수 | COMPLETED, 요청 시각 → 종결 시각 (DB) |
| TPS 로컬 | 초당 커밋된 쓰기 로컬 트랜잭션 수 | AOP 트랜잭션 시작 → 커밋 시각 |

- 지연 시간은 p50, p95, p99로 기록한다
- 지연 시간은 부하로 인해 지연된 시간이 포함된다

### 세부 구현

- VirtualThread 기반으로 개방형 부하 생성
- TransactionExecutionListener를 통해 트랜잭션 변경 감지
- 클라이언트는 Spring에서 제공하는 RestClient 사용

### 지연 문제

- 전체 주문을 처리하는 과정에서 p95, p99가 떨어지는 꼬리 지연이 발생함
- 각각의 로컬 트랜잭션을 처리하는 시간은 길지 않다
- RPS 시간은 재고 + 계좌 트랜잭션 + 50ms 내외로 차이가 크지 않다
- 따라서 약 2초의 지연은 **배송 메시지 발행 · 소비 구간**에서 발생한다

다음 해결책을 순차적으로 진행하며 TPS를 관찰한다.

1. 다음 로컬 트랜잭션을 묶어 한 번에 처리한다
2. 소비자에서 메시지를 배치처리한다
3. Debezium 풀링 주기를 줄인다
4. 파티션과 소비자를 스케일아웃한다 (생략)
